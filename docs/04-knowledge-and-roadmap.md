# 04：优化知识库、研究验证与实施路线

## 1. 从单个引擎走向优化范式

VibeForge 的长期目标是把“某次修改变快了”转化为能够指导下一次生成的知识：

```text
模型 / 硬件 / 负载特征
→ 可观测瓶颈及确认方法
→ 适用的优化策略
→ 具体实现步骤与参数选择
→ 正确性和性能验证
→ 收益范围、代价、失效条件及反例
```

知识库采用类似 skill 的结构：既说明何时使用，也给出可执行步骤和验收方法。首阶段使用普通版本化文档与结构化索引即可，不要求绑定某一种 Agent 平台。

## 2. 三类信息分开管理

| 层次 | 保存内容 | 能否直接作为经验推荐 |
| --- | --- | --- |
| 实验档案 | 每轮事实、原始数据、差异、决策和分析 | 仅用于检索与复核 |
| 局部经验 | 某个固定画像上的重复验证结论 | 仅在相同或已验证条件下推荐 |
| 优化规则 | 明确特征条件、实现方式、验证证据和反例的可迁移条目 | 按适用范围与置信状态推荐 |

一次成功先产生局部经验。多个形状上的重复测试可以增强局部证据，但不等同于跨模型或跨硬件验证。

## 3. 知识条目结构

| 字段 | 内容 |
| --- | --- |
| 标识与状态 | `rule_id`、版本、草案/局部验证/跨配置验证/失效 |
| 目标问题 | 解决哪类瓶颈，优化哪个主指标 |
| 适用条件 | 模型结构、张量形状、精度、设备能力、软件环境与负载区间 |
| 排除条件 | 不支持的形状、质量约束、内存限制、已知冲突 |
| 前置诊断 | 需要什么测量来确认瓶颈，而不是只凭设备型号猜测 |
| 实现步骤 | 应修改的执行路径、算法、布局、参数、构建选项 |
| 验证步骤 | 局部数值测试、端到端测试、基准协议、回退条件 |
| 实测效果 | 基线与优化值、不确定性、负载、资源与质量代价 |
| 支持证据 | 活动、版本、实验、原始样本与报告引用 |
| 反例与交互 | 在何处退化，与哪些规则相互依赖或冲突 |
| 维护信息 | 来源、修订原因、最后验证环境和时间、替代条目 |

### 3.1 条目模板

```markdown
# <规则名称>

状态：草案 / 局部验证 / 跨配置验证 / 失效
目标：<主指标与要解决的瓶颈>

## 触发条件
- 模型、硬件、负载、精度与软件环境条件。

## 前置诊断
- 需要采集的指标，以及支持或否定瓶颈假设的观察。

## 实现方法
1. 代码入口和执行路径。
2. 算法、布局、调度或参数修改。
3. 边界处理和不支持时的回退路径。

## 验证方法
- 正确性、性能、资源与 Agent 可用性检查。

## 证据与适用范围
- 实验引用、收益原值和区间、已经验证的配置。

## 代价、反例与冲突
- 质量、内存、启动成本、其他负载退化和规则交互。

## 下一步
- 尚未验证的条件与下一次最小实验。
```

条目应包含实现示例或指向经过验证的代码差异。只有“可以融合算子”“尝试量化”等泛泛建议，不足以成为可执行知识。

## 4. 知识生成与检索闭环

```mermaid
flowchart LR
    E[完整实验及失败档案] --> L[提取局部经验]
    L --> R[形成候选规则]
    R --> V[重复、消融与跨配置验证]
    V --> K[带条件的知识库]
    K --> Q[按当前画像与瓶颈检索]
    Q --> A[Agent 选择下一轮假设]
    A --> E
    V -->|反例或失效| U[缩小范围、修订或停用]
    U --> K
```

### 4.1 何时可以提升为规则

1. 修改和结果可复现，且存在完整的基线与原始数据。
2. 有重复测量支持，能排除已识别的测量污染。
3. 对主要收益来源有证据；联合变更应补充消融或注明归因未确定。
4. 明确已验证与未验证的模型、设备、负载和软件条件。
5. 保存失败配置与代价，不因总体平均收益而隐藏局部退化。
6. 跨配置验证满足预先设定的覆盖要求后，才能标记为可迁移规则。

知识条目与引擎版本分别管理。某个候选被拒绝，也可能产生有用的反例或“在另一负载下再验证”的研究线索。

### 4.2 下一轮如何使用知识

- 先按模型结构、设备能力、精度、负载和软件条件筛选。
- 再结合当前 profiler 证据，选择能够解释当前瓶颈的规则。
- 优先使用适用条件明确、证据充分、实施成本较低的条目。
- 同时展示反例、冲突规则和此前失败实验，避免重复无效尝试。
- 记录本轮使用了哪些规则及版本，后续才能评估知识库是否有效。

知识条目是待验证的行动依据，不代替本地评测。依赖、驱动或模型发生变化后，相关规则需要重新确认。

## 5. 初始优化方向：作为假设，不作为既定结论

下表只用于组织搜索空间。每一项都需要先观察瓶颈，再在本机验证；当前文档没有提供任何实测收益。

| 特征与观察 | 可探索方向 | 实现与验证重点 |
| --- | --- | --- |
| 固定模型和常用张量形状，动态分支占明显开销 | 形状特化、预计算、减少运行时分派 | 明确支持形状，保留边界回退，比较完整请求时延 |
| 小批量 decode，观察到访存受限 | 权重布局、访存合并、允许时探索低精度 | 证明实际数据搬运或等待减少，同时检查数值和质量 |
| 长输入 prefill，计算热点明确 | 分块矩阵计算、注意力实现、算子融合 | 覆盖输入长度、掩码、头映射、位置编码与内存峰值 |
| 短请求中大量小算子或设备启动 | 合并执行、减少同步、复用执行计划 | 测量启动开销与端到端收益，记录额外编译和缓存成本 |
| 长上下文下 KV cache 成为内存瓶颈 | 缓存布局、分配与回收策略；协议允许时研究缓存低精度 | 逐步 decode、多请求隔离、上下文上限和质量 |
| 多并发服务，队列等待或碎片明显 | 批处理、调度、缓存管理 | 同时比较吞吐、公平性、p95/p99 时延与内存 |
| 共享内存设备上有冗余复制或内存压力 | 减少复制、调整缓冲区与数据生命周期 | 区分主机与设备访问，核实同步与一致性，避免重复统计内存 |
| 稀疏专家模型中路由和小计算占比高 | 专家分组、调度、路由数据布局 | 路由正确性、负载不均、额外缓冲与实际激活模式 |

同一个策略可能改善一个负载、损害另一个负载。知识库必须记录条件和权衡，不能只保留“某策略能加速”的结论。

## 6. 如何验证研究目标

### 6.1 分别回答四类问题

| 研究问题 | 核心证据 |
| --- | --- |
| 能否生成可运行的专用引擎？ | 功能覆盖、正确性通过率、生成代码与复用依赖边界 |
| 能否可靠地自主迭代？ | 自主完成率、恢复成功率、人工介入次数、每轮成本 |
| 是否带来真实部署收益？ | 同条件下的性能、资源、质量、部署体积与启动成本 |
| 是否形成可迁移的优化范式？ | 新配置上的命中率、试验次数、验证成功率和新增收益 |

### 6.2 比较基线

- 可信通用引擎：在相同模型、精度、硬件和负载下，使用合理配置作部署基线。
- 初始轻量引擎 `v0`：衡量自优化的累计收益。
- 仅参数调优：区分配置搜索与生成或修改引擎代码的贡献。
- 无知识库的 Agent：衡量经验检索是否减少试错和改善最终结果。
- 自托管与外部辅助模式：分别统计，判断本地目标模型能否独立完成循环。

比较时披露软件环境、功能范围、Agent 预算、调优预算和人工投入。若模型或硬件无法支持某个基线，应说明缺项，不能将其计为自动获胜。

### 6.3 消融与迁移实验

| 实验 | 目的 |
| --- | --- |
| 仅原始日志 vs 日志加结构化分析 | 评估分析对重启后决策与重复试错的影响 |
| 有知识检索 vs 无知识检索 | 评估知识库对搜索成本和收益的贡献 |
| 配置调整 vs 配置加代码生成 | 区分收益是否来自引擎生成 |
| 同一策略的不同实现或组合消融 | 验证因果归因和策略交互 |
| 未参与规则形成的模型、设备或负载 | 验证迁移能力，限制泛化结论的范围 |
| 受控注入 Agent、引擎和控制程序故障 | 验证恢复与日志完整性 |

研究报告除最优结果外，还应给出失败比例、无显著收益比例、总搜索成本和多个独立活动的结果分布，避免仅展示偶然成功的一轮。

## 7. 分阶段实施

| 阶段 | 交付物 | 退出条件 |
| --- | --- | --- |
| P0：固定实验目标 | 一组模型/硬件/负载画像，评测协议，可信参考，初始 `v0` | 可重复评测，`v0` 可运行 Agent，稳定制品可重新拉起 |
| P1：可靠控制闭环 | 状态机、版本隔离、准入、回退、事件日志、恢复资料 | 通过故障注入；重启后状态一致，失败候选不覆盖稳定版 |
| P2：Agent 自动迭代 | 假设模板、代码修改工具、结果分析、预算与停止条件 | 多轮无人干预完成，结果可复现，每轮证据与分析可追溯 |
| P3：扩大生成深度 | 热点诊断、算子或执行路径生成、分层数值验证 | 证明配置调优之外的收益，并保持正确性与可恢复性 |
| P4：经验抽象与迁移 | 知识条目、特征检索、反例管理、独立迁移实验 | 在新配置上证明确有帮助，明确规则边界与失败条件 |

P1 可以先由脚本或固定候选模拟 Agent 交付，单独验证控制可靠性；P2 再接入真正的自托管 Agent。这样能够区分基础设施故障和优化能力不足。

### 7.1 第一阶段建议收窄的范围

- 一台设备、一个文本生成模型、固定精度和上下文上限。
- 一组代表性输入/输出长度，先单请求，再逐步加入并发。
- 一个主性能目标，少量明确的保护指标。
- 先实现配置和小范围代码修改，再扩展到专用内核生成。
- 先使用本地持久化文件或数据库，完整保留实验材料，再增加看板与检索能力。

### 7.2 控制闭环验收清单

- [ ] 正确候选有可复现收益时，能提升并用于下一轮 Agent。
- [ ] 正确性失败、资源超限、性能退化时，稳定版本不被替换。
- [ ] 收益不显著时，能复测或维持稳定版本，并记录原因。
- [ ] Agent 崩溃、候选崩溃、评测超时后，都能恢复已验证服务。
- [ ] 切换前后重启控制程序，不会重复提升或丢失回退目标。
- [ ] 整机重启后，可以仅依赖持久化状态与日志继续活动。
- [ ] 新 Agent 能说明上一轮改动、结果、待验证原因和下一步假设。
- [ ] 每个收益结论都能追溯到代码、协议、原始样本和环境。
- [ ] 达到预算、重复失败或无法恢复时，系统能停止并报告。

## 8. 开始实现前需要固定的配置

| 配置 | 需要作出的选择 |
| --- | --- |
| 首个部署目标 | 哪个模型、精度、设备及软件环境 |
| 自举来源 | 参考后端、已有最小引擎、是否允许外部 Agent 辅助 |
| 工作负载 | 输入/输出长度、并发、上下文、工具调用能力 |
| 正确性契约 | 数值容差、任务质量、是否允许量化或近似 |
| 优化目标 | 主指标、保护指标、最小收益、统计和复测规则 |
| 生成范围 | 配置、执行路径、算子、内核分别允许改到什么程度 |
| 运行预算 | 时间、轮数、资源、重试次数和停止条件 |
| 存储策略 | 日志位置、刷盘策略、证据保留、恢复版本数量 |

这些是后续实现的活动配置项，当前文档不代替具体实验选择，也不假定尚未测量的性能收益。
