# 03：评测、实时日志与上下文恢复

## 1. 评测协议先于优化

Agent 不能用“看起来更快”作为提升版本的依据。每次活动开始前，固定下列协议并计算哈希：

| 项目 | 固定内容 |
| --- | --- |
| 身份 | 模型、分词器、模板、硬件画像和参考实现版本 |
| 测试 | 用例、输入 token、生成参数、随机种子、形状和并发组合 |
| 正确性 | 精度容差、允许的近似策略、质量下限、功能契约 |
| 性能 | 主指标、保护指标、负载权重、测量边界与计时方式 |
| 统计 | 预热、重复次数、采样分组、置信方法、最小有效收益和复测上限 |
| 约束 | 内存上限、失败率、超时、上下文长度、依赖或部署体积预算 |

协议变化需要生成新版本；影响可比性的变化应新建活动并重新建立基线。新增回归用例可以持续积累，但必须标明各版本实际使用的测试集。

## 2. 正确性：从局部到完整执行

| 层次 | 检查内容 | 典型失败 |
| --- | --- | --- |
| 构建与接口 | 可构建、可启动、加载权重、生成接口与错误处理 | 依赖错误、权重缺失、返回格式不兼容 |
| 算子数值 | 对参考实现比较代表形状和边界形状 | 分块尾部错误、布局错误、低精度误差异常 |
| 模型数值 | 隐藏状态或 logits、prefill、逐步 decode | 位置编码错误、注意力掩码错误、误差累积 |
| 状态与缓存 | KV cache 增长、复用、回收，多请求隔离 | 缓存越界、请求间污染、长序列失效 |
| 生成语义 | 分词、模板、特殊 token、EOS、停止条件、采样参数 | 输出语义或完成原因错误 |
| 服务稳定性 | 长时运行、并发、取消、重复请求、内存变化 | 泄漏、死锁、资源无法释放 |
| Agent 可用性 | 模型响应解析、工具调用、最小任务、上下文恢复 | 引擎可生成文本但无法支撑 Agent 工作 |

按模型实际特征选择测试：例如，具有专家路由的模型需覆盖路由与专家计算；分组查询注意力模型需覆盖对应的头映射。未支持的功能应明确声明，不能通过缺少测试隐式算作支持。

### 2.1 参考与判定方式

- 参考来源是固定的可信实现或提前生成、带版本标识的参考材料，不能由候选自己充当正确性裁判。
- 浮点运算通常需要预先约定绝对误差、相对误差等标准；不默认要求所有后端逐位一致。
- 固定种子有助于复现，但不保证不同内核在采样生成时逐 token 相同。数值比较与生成质量检查分别报告。
- 允许量化或近似计算时，额外固定质量评测与允许损失，不能在看到性能后临时放宽标准。
- 对发现的失败增加最小复现用例；用例及其期望结果经过独立确认后纳入回归集。

### 2.2 评测独立性

| 材料 | 使用方式 |
| --- | --- |
| 开发集 | Agent 可读取，用于定位与局部调试 |
| 回归集 | 控制程序固定执行，覆盖已知故障与功能边界 |
| 保留集 | 在里程碑或最终验证时使用，降低对固定测试的过拟合 |

Agent 提供的自测是辅助证据，正式准入仍由固定评测器执行。最终研究报告披露测试集范围和未覆盖能力。

## 3. 性能指标与优化目标

| 指标 | 含义与使用场景 |
| --- | --- |
| TTFT | 从约定的请求起点到第一个输出 token 的时间，反映首 token 响应 |
| TPOT / ITL | 首 token 后的平均每 token 时间 / token 间延迟分布，反映持续生成体验 |
| Prefill 指标 | 固定输入规模下的处理时延或输入吞吐 |
| 输出吞吐 | 测量窗口内完成的输出 token 总数除以窗口时间，注明并发和统计规则 |
| 请求时延 | 完整请求的 p50、p95、p99，以及失败率和超时率 |
| 内存 | 主机、设备及共享内存的峰值与稳态占用，避免共享内存重复计算 |
| 启动成本 | 加载、编译、预热和服务就绪时间，区别于稳态推理性能 |
| 能耗与资源 | 有可靠测量条件时记录每请求或每 token 能耗、利用率与频率 |
| 轻量化指标 | 必需依赖、部署体积、生成代码规模、构建和移植成本 |
| Agent 端到端表现 | 固定优化任务的成功率、完成时间和推理成本，作为系统层补充指标 |

当输出 token 数 `N > 1` 时，可按 `(最后 token 时间 - 首 token 时间) / (N - 1)` 定义 TPOT。流式时延与设备内核时延分开统计；设备执行计时需要正确处理异步操作。

### 3.1 一个主目标，加若干保护指标

示例目标形式，具体数值在活动配置中确定：

```text
主目标：固定并发与输入/输出长度组合下，提高加权输出吞吐。
保护指标：p95 首 token 时延、峰值内存、失败率不超过预设界限。
硬约束：正确性通过，支持约定上下文与功能，部署资源不超预算。
```

也可以选择“降低单请求 decode 时延”等其他主目标。多目标实验需预先定义排序规则或维护 Pareto 候选集，并明确哪个版本用于自托管，不能事后挑选最有利指标。

## 4. 如何确认收益

### 4.1 可比较的测量流程

1. 检查环境、频率与功率设置、温度、后台任务和设备剩余资源。
2. 为稳定版和候选版使用相同负载与计时边界，分别充分预热。
3. 在同一设备上按预设顺序交错运行两版，例如交替或随机化顺序。
4. 按负载组合进行多轮测量，保存每次原始样本及当时设备状态。
5. 将无效样本及原因保留，但从正式统计中按预设规则排除。
6. 计算主指标收益、不确定性和保护指标，交由准入判定器处理。

保持输入 token 和生成工作量可比。固定长度性能测试与自然 EOS 的功能测试分开定义；不能通过少生成 token 或改变回答语义取得表面收益。

### 4.2 收益公式

| 指标方向 | 收益表达 |
| --- | --- |
| 越高越好，如吞吐 | `候选值 / 稳定版值 - 1` |
| 越低越好，如时延 | `1 - 候选值 / 稳定版值` |

报告必须注明指标、原值、分母和工作负载。不要将“时延降低比例”与“吞吐提高比例”混为同一个数值。

### 4.3 统计与决策

- 最小有效收益记为 `ε`，保护指标容许退化记为各自的 `δ`，在活动开始前固定。
- 可采用配对运行组的收益置信区间：主指标收益下界超过 `ε`，且保护指标满足约束，才允许提升。
- 置信水平、样本数量、聚合权重和估计方法必须预先配置；不能默认样本充分或相互独立。
- 同一运行中的 token 往往相关，宜以独立运行或负载组为统计单位，避免把大量 token 当作独立重复。
- 证据不足时有限复测；预算用尽仍不明确，则维持稳定版本，并记录“无显著收益”。
- 多轮搜索会增加偶然胜出的机会。里程碑版本使用独立确认测量与保留负载，再报告最终收益。

这些规则不要求首版实现复杂统计系统，但首版也必须保留原始样本、重复测量和明确的最小收益门槛。

### 4.4 单轮与累计收益

- 单轮收益：候选相对当前稳定版，在本轮同条件下比较。
- 累计收益：最终稳定版相对初始 `v0`，在统一协议下重新测量。
- 历史测量可供分析，不能在环境不同的情况下直接拼接成累计提升。

## 5. 日志是恢复和研究的数据基础

### 5.1 分层保存

| 层次 | 记录什么 | 用途 |
| --- | --- | --- |
| 结构化事件 | 状态迁移、命令、动作开始与结束、版本、决策、指标引用 | 实时监控、审计、状态对账与恢复 |
| 原始证据 | 标准输出、标准错误、堆栈、逐次测量、设备采样、代码差异 | 复现问题、重算统计、验证分析 |
| 实验报告 | 假设、改动、结果、因果解释、替代解释、下一步 | 新 Agent 理解实验和研究人员审阅 |
| 上下文快照 | 当前稳定版、最近结论、未完成操作、待分析项、历史索引 | 每次重启时快速恢复工作 |
| 知识条目 | 有适用条件与证据的优化步骤和反例 | 跨活动复用优化经验 |

**事实、分析和建议分别标记。**“观察到时延下降”是事实；“推测来自访存减少”是解释，需要 profiler 或消融实验支持。

### 5.2 统一事件字段

| 字段 | 说明 |
| --- | --- |
| `event_id / sequence` | 全局事件标识与活动内单调序号，用于去重、排序和检测缺口 |
| `timestamp / monotonic_time / boot_id` | 墙钟时间、当前系统启动内单调时间、系统启动标识 |
| `campaign_id / iteration_id / operation_id` | 活动、迭代、动作关联关系 |
| `session_id / actor / event_type` | 哪个 Agent 或控制模块执行了什么 |
| `state_before / state_after` | 状态变化；普通日志事件可为空 |
| `stable_ref / candidate_id` | 与哪个版本相关 |
| `profile_hash / protocol_hash` | 使用哪份环境画像和评测协议 |
| `payload / artifact_refs` | 命令参数、退出码、原因码、测量摘要及原始材料位置与哈希 |

示意事件，尖括号为占位符，不是实际运行结果：

```json
{
  "event_id": "<unique-event-id>",
  "sequence": 42,
  "timestamp": "<UTC-ISO8601>",
  "boot_id": "<boot-id>",
  "monotonic_time": 120.5,
  "campaign_id": "<campaign-id>",
  "iteration_id": "<iteration-id>",
  "operation_id": "<operation-id>",
  "session_id": "<session-id>",
  "actor": "evaluator",
  "event_type": "benchmark_started",
  "state_before": "VALIDATING",
  "state_after": "BENCHMARKING",
  "stable_ref": "<stable-version>",
  "candidate_id": "<candidate-version>",
  "profile_hash": "<profile-hash>",
  "protocol_hash": "<protocol-hash>",
  "payload": {"measurement_group": "<group-id>"},
  "artifact_refs": []
}
```

### 5.3 实时性与持久性

- 动作执行前写入开始事件，执行后立即写入完成、失败或超时事件；每个长动作有心跳。
- stdout、stderr 和设备采样持续采集到独立文件，事件流引用文件位置。
- 普通输出按配置的短周期刷新；明确其掉电时可能丢失的最大缓冲窗口。
- 关键状态、决策、版本切换意图与结果必须持久化后再推进，不能仅依赖内存队列。
- 墙钟时间用于展示和跨进程关联；时长使用单调时钟，不跨系统重启直接相减。
- 事件流追加写入；修正结论使用新事件和新报告版本，不覆盖历史事实。
- 定期建立检查点、轮转日志和校验归档。实时界面从持久化事件构建，界面不是唯一数据源。

### 5.4 实时看板应显示什么

当前状态与心跳、稳定版本与候选版本、正在执行的操作、已完成测试、原始性能与收益区间、设备资源、最近拒绝原因、剩余预算、日志入口。

最终报告还应列出累计接受与拒绝次数、有效与无效测量数、各轮收益、恢复事件及知识条目的证据链接。

## 6. 持久化目录

工程目录及首版运行程序已实现，完整说明见 [项目目录与文件放置规范](05-project-layout.md)。下面的活动、发布版本和单轮实验目录由运行程序按需创建；现有验证档案入口见 [验收报告](07-implementation-validation.md)。本章仍描述目标协议，具体覆盖范围以验收报告为准。

```text
VibeForge/
├── src/vibeforge/                # 控制、Agent、引擎适配、评测等源码
├── configs/                      # 声明式活动与评测配置
├── benchmarks/                   # 固定用例与可信参考材料
├── templates/                    # 引擎、提示词、报告和知识模板
├── knowledge/                    # 经整理的优化知识内容
├── docs/                         # 设计与使用文档
└── var/
    ├── state/                    # 权威状态、锁、检查点
    ├── profiles/                 # 模型、硬件、环境和负载画像
    ├── workspaces/               # 可写候选源码与临时构建输出
    ├── releases/<version>/       # 不可变发布清单与构建制品
    ├── cache/                    # 可重建的下载、编译和知识索引缓存
    └── campaigns/<campaign-id>/
        ├── manifest.json        # 活动目标、预算与协议引用
        ├── configs/             # 启动时冻结的配置快照
        ├── events/              # 追加式结构化事件
        ├── resume/              # 可重建的上下文快照
        ├── knowledge-drafts/    # 待验证的经验和规则草案
        ├── summary.md           # 活动总结
        └── iterations/<iteration-id>/
            ├── hypothesis.md    # 事前假设与预期
            ├── candidate.json   # 父版本、哈希与产物引用
            ├── change.patch     # 代码差异
            ├── commands.jsonl   # 工具动作、参数、工作目录和结果
            ├── logs/            # 构建、引擎、Agent 的原始输出
            ├── correctness/     # 用例、参考结果与误差
            ├── benchmarks/      # 原始测量、设备状态与汇总
            ├── decision.json   # 准入结果、原因和证据
            └── analysis.md     # 事实、解释、反例与下一步
```

源码目录不替代不可变发布制品。保留策略不得删除当前及必要恢复版本，或仍被研究结论引用的证据。

## 7. 重启后的上下文恢复

### 7.1 分层读取，避免每次灌入全部历史

| 层次 | 内容 | 读取时机 |
| --- | --- | --- |
| 固定约束 | 当前目标、权限边界、正确性与准入协议 | 每次启动必读 |
| 当前快照 | 稳定版本、最后状态、最近决策、剩余预算 | 每次启动必读 |
| 最近分析 | 上轮假设、实际差异、结果、失败原因、待验证问题 | 每次启动必读 |
| 历史索引 | 已尝试方案、有效条件、失败模式、证据位置 | 决定下一步前查询 |
| 原始证据 | 代码、样本、profile、详细日志 | 按问题检索 |

上下文快照带生成序号及来源引用。它是可重建的缓存；与权威状态不一致时，以控制程序对账后的状态和原始证据为准。

上一轮分析完成并持久化后，才允许提交下一轮候选；活动结束时也要安排最后一轮的分析，避免只留下测量而没有解释。

### 7.2 Agent 启动任务模板

```text
1. 确认活动、稳定版本、目标画像、协议和剩余预算。
2. 判断上一轮是否完整结束；核实未完成或待分析操作。
3. 阅读上轮证据，完成 analysis_pending 的分析。
4. 查询已试方案和相关知识，说明本轮与历史尝试的区别。
5. 提出一个可证伪的优化假设、预计影响及验证方法。
6. 在分配的候选工作区实施修改，提交候选与恢复备注。
```

### 7.3 每轮分析必须回答

- 原先认为瓶颈是什么，依据是什么？
- 实际修改了哪些执行路径，是否存在混杂变更？
- 正确性、性能与资源分别发生了什么变化？
- 收益或失败的解释有哪些，哪些已经验证、哪些仍是假设？
- 什么条件下值得重试，什么条件下应放弃？
- 是否需要新增回归用例、更新知识条目或纠正旧结论？

日志负责保存完整事实，恢复资料负责高效定位，分析负责形成下一步可验证的判断。三者都应在每轮闭环中留下明确产物。
